1. Data Security & Commercial Hardening

To safely sell software to commercial enterprises, retail stores, and supermarkets, the system implements a defense-in-depth model across the network layer, desktop runtime, database, and source code:

Security Layer Threat Addressed Implemented Protection
Network Boundary Rogue Wi-Fi snooping; unauthorized access from phones or devices on the store network. Express backend is strictly bound to 127.0.0.1 (Localhost only). Remote external devices on Wi-Fi are completely rejected by the kernel.
Electron Sandbox Malicious scripts or browser exploits gaining OS access. contextIsolation: true, nodeIntegration: false. External window popups and arbitrary navigation are blocked.
Developer Tools Lock Cashiers or staff pressing F12 / Ctrl+Shift+I to inspect or tamper with sales data. DevTools are disabled in production builds. Web preferences lock inspection capabilities for end users.
Source Code Protection Clients or competitors reverse-engineering, modifying, or stealing proprietary business logic. Packaged using Electron ASAR archive ("asar": true) + minified client assets. Code is sealed inside binary archives.
SQL Injection Prevention Malicious inputs in barcode search, customer names, or invoice notes altering the database. 100% of SQLite database queries use parameterized prepared statements (? placeholders). Raw string concatenation is prohibited.
Authentication & PIN Cashiers viewing financial reports, modifying stock, or altering past transactions. Role-based permissions dividing standard cashier billing from Manager/Admin areas (Reports, Purchases, Settings).

2. Power Cut & Crash Resilience Architecture

Supermarkets frequently suffer unexpected power outages, accidental cable pulls, or hardware restarts. The system is architected to guarantee zero data corruption during sudden loss of power.

┌────────────────────────────────────────────────────────────────────────┐ │ SUDDEN POWER CUT RESILIENCE FLOW │ ├────────────────────────────────────────────────────────────────────────┤ │ 1. Transaction Starts ➜ Cashier completes sale / invoice checkout. │ │ 2. WAL Append Only ➜ Data writes sequentially to database.sqlite-wal.│ │ (Main database.sqlite is NEVER touched!) │ │ │ │ 🛑 POWER CUT HAPPENS HERE (Zero milliseconds warning) │ │ │ │ 3. On Reboot (Re-launch)➜ SQLite auto-detects uncheckpointed WAL file. │ │ 4. Atomic Recovery ➜ Completed sales replayed into main DB in 10ms.│ │ Incomplete sales cleanly rolled back. │ │ 5. Result ➜ Zero corrupted tables; zero database loss. │ └────────────────────────────────────────────────────────────────────────┘
Why SQLite WAL (Write-Ahead Logging) is Critical: In traditional databases, power cuts during file writes cause "torn pages", corrupting the database file permanently. In WAL mode, the active database file is read-only during transactions. Changes are appended to the WAL file first, ensuring full ACID compliance.

3. 3-Tier Redundant Backup Engine

To eliminate data loss under any circumstance (disk failure, virus, theft, or operator error), SuperMart POS runs a 3-tier redundancy pipeline:

Tier Storage Destination Trigger Frequency Purpose
Tier 1: WAL Log %APPDATA%/.../database.sqlite-wal Every transaction Sub-second recovery from sudden power cuts.
Tier 2: Local Backups %APPDATA%/.../backups/*.sqlite On Startup & App Close Offline air-gapped recovery if the main database is damaged. Keeps last 5 snapshots.
Tier 3: Cloud / External G:\My Drive\POS_Backups\ or USB Startup, 15-min interval, and Shutdown Total hardware failure / theft protection. Restorable on any laptop in 30 seconds.

Atomic File Synchronization with `fsync`

To prevent 0 KB truncated files during shutdown or unexpected termination, backup transfers use atomic multi-stage validation:

  • Data is written to a temporary staging file (.tmp_[timestamp]) using a dedicated 128KB buffer.
  • Operating system flush command (fsyncSync) forces the physical drive / Google Drive cloud driver to commit all bytes to disk before returning.
  • File size is verified (must equal at least 95% of master DB). Only then is it atomically renamed to replace the target.
  • If the process is interrupted at any microsecond, the existing healthy backup file remains completely untouched.

4. Disaster Recovery Runbook (Step-by-Step)

If a client's computer dies, hard drive is corrupted, or a machine is replaced, follow these steps:

1 Download Newest Backup: Open Google Drive (or attach the backup USB drive) and download the latest database.sqlite or backup_YYYY-MM-DD.sqlite snapshot.
2 Install SuperMart POS: Run the SuperMart-POS-Setup.exe installer on the new machine.
3 Restore Database: Press Win + R, type %APPDATA%\supermart-desktop-pos, and press Enter. Paste the downloaded database.sqlite file into this folder.
4 Launch: Open SuperMart POS. All historical sales, stock levels, GST ledgers, and settings are 100% restored.

5. Packaging into Electron for Commercial Distribution

When wrapping and distributing the software to customers:

  • Installer Type: Packaged as an NSIS single-click Windows Installer (.exe).
  • Data Preservation: All databases, uploads, and backups are stored in the client's Windows User Data folder (%APPDATA%\supermart-desktop-pos). When the client installs software updates, their database is preserved and never deleted.
  • Port & Process Auto-Healing: If port 5000 is occupied by a stale process, the launcher detects and terminates the collision automatically. If the backend experiences an uncaught error, Electron restarts the server without crashing the user interface.
